# 云同步扩容与分块传输

1.0 新客户端通过 `/v1/vault/chunks` 协商 `X-CShell-Vault-Transport: 1`，仍使用原 AES-256-GCM 保险库和账号 AAD，不改变恢复密钥。分块是密文传输机制，不是修改加密格式。

## 传输与恢复

- 上传先提交 mutationId、baseRevision、nonce、密文长度及 SHA-256。每块最多 1 MiB Base64 字符，分块与整份密文分别校验摘要。
- 服务端返回已接收块编号。响应丢失后使用持久化的同一 mutationId 续传，不重新上传已确认块。提交前再次核对版本和额度，在一个 SQLite 事务内切换整份保险库。
- 下载使用固定 revision，逐块摘要校验；加密缓存保存到客户端私有目录。同 revision 中断后继续，云端版本改变则拒绝混合块，下一轮重新开始。缓存只保留当前下载版本。
- 断点暂存最长 24 小时，每账号一份上传，全服务最多 1 GiB 未提交密文；不挤占已有正式保险库。摘要错误、未完成上传和 CAS 冲突均不改变云端当前版本。
- 旧 `/v1/vault` 接口仍可访问 64 MiB 以内保险库；更大内容在加载前返回明确升级提示，禁止旧客户端截断写回。只有确认新端点不存在（404）才回退旧接口，块丢失或协议不符不能悄悄回退。

## 容量不是内存承诺

账号扩容量最高 256 MiB，管理员配置保留原权益。不同终端另行声明安全可读容量：桌面依据启动时可用内存的 1/24，最高 256 MiB；Android 依据 JVM 最大堆的 1/24，最高 256 MiB。服务端在发出任何数据块前检查设备容量。不足时提示使用更大内存设备，保留云端、本机及已配置扩容权益。

现有保险库导入/合并仍需要完整 JSON 对象；分块限制网络缓冲与服务器内存，不能宣称完整客户端处理恒定 1 MiB。桌面存在密文、解密对象、备份、冲突基线等峰值副本，Android 不应盲目把固定 64 MiB 提升成 256 MiB。

## 本地验证

- `test_vault_chunks.py`：65 MiB 分块跨服务实例重启续传、提交、旧端拒绝；Python 分块逻辑 tracemalloc 峰值小于 10 MiB。摘要错误、部分提交、账号隔离、并发版本冲突、超额及暂存到期清理均覆盖。
- `scripts/cloud-chunks-integration.ts`：真实本地 HTTP、65 MiB AES-GCM 保险库、丢失上传响应、下载中断后恢复、完整 CloudSync 上传、加密状态与备份、第二台桌面恢复。该单进程同时保留两台客户端与测试副本，实测峰值 RSS 1331 MiB，结束 RSS 729 MiB。使用临时数据库和测试凭据，不接触生产账号。
- `CloudVaultChunksTest.java`：JVM `-Xmx64m` 下 3 MiB 下载中断恢复，过量清单在分配大对象前拒绝。Android Java 编译通过；这不是手机 256 MiB 的实机通过记录。

## 发布顺序

先部署 `vault_chunks.py` 与对应 `server.py`，自动创建分块表；再发客户端。反向代理需保留版本/容量请求头，允许每块至少 1 MiB+4 KiB 的请求体。无须提高到整份 350 MiB 请求。保留旧保险库表及旧端点，回滚时应使用支持分块读取的服务器版本，不能直接回滚到忽略分块表的旧服务。
